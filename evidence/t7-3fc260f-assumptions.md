## 2. 建模選擇

1. **模擬核心不變**：`sim/t7-3fc260f/core.js` 複製自 `sim/t7/core.js`，只加記 `tideDoneSum`／`tideDoneN`（完成的獸潮件 出現→完成 的小時）。
   - 情境流程、亂數序列、樣本組（200／2400／200）、種子、就寢模式都與上一輪相同。
   - 掃描點同樣是 10416 個，seed 20261128。
2. **新規則**：直接呼叫 vm 載入的 `G.wakeTime`。舊規則用 v0.3：`sim/lib/time.js:66` 的 `wakeNew`，即 `max(now+6h, 下一個 08:00)`。另外列 main 現況缺陷（`wakeOld`）當資訊。
3. **「延誤平均只算有完成的件數」**：判準用全樣本加權平均，也就是 Σ 完成件延誤 ÷ Σ 完成件數。0 完成的情境對分子、分母都不貢獻，不記 +∞。
   - 另外列「各情境平均的平均」（只計有完成的情境）當交叉檢查，兩種算法的結論方向一致。
4. **延誤類用兩個門檻指標，兩者都要 新 ≤ 舊**：
   - B 完成件延誤（傳聞＋獸潮）。
   - 配對獸潮延誤，只算完成的獸潮件。
   - 上一輪的「配對獸潮延誤（未完成記到期）」改列資訊，因為它把未完成件記成到期時數，不符合「只算有完成件數」。
   - 兩個門檻指標都要求新 ≤ 舊，比只看其一更嚴，沒有放寬。
5. **0 完成情境數**：B（有處理）在 60 天內完成 0 件的情境數，新／舊各自計數，判準是新 ≤ 舊。
6. **期限／過期類**：沿用上一輪三項，逐情境比對新 > 舊即算違反，三組都要 0。
   - A：不處理時，期限落在睡過頭時段。
   - B：過期。
   - B：因睡過頭而過期。
7. **飽食的「實測未取整扣減」**：實作把飽食存成整數（`js/game.js:487`，`Math.round`），不能直接讀到 7.5 這類值。量法如下：
   - 起始飽食取非整數 x ∈ [50.123, 51.123)，用二分法找出睡後整數結果翻轉的 x*。
   - c = x* − (翻轉後值 − 0.5)。
   - 每一步都是真的呼叫 `G.service`。
   - 判準是 c 與 1.25×h×(冬 1.25) 相差 < 1e-6，並且起始 80 的整數結果 = round(80 − 規格)。
8. **hp 規格模型**：依實作的 `passTime` 一次結算來建，用來逐案比對 rest／bunk：
   - 飽食扣完 ≤0 時，斷糧扣 3×h；疲累 ≥100 時，力竭扣 2×h（睡眠的 df=0，疲累不變）。
   - 下限 1，再取整。
   - rest 醒來：maxHp（侵蝕 −10 後）。bunk 醒來：min(maxHp, hp+30)。
   - 上界：rest 是 maxHp，bunk 是 min(maxHp, 睡前 hp+30)。
9. **「hp 100」案例**：開局 maxHp 是 80，hp 100 會超過上限。所以這個案例把體（ti）設成 20，使 maxHp = 110。其他案例 ti=10，maxHp 80。
10. **露宿案例的設定**：
    - 地點：赤石廢礦（地點險級「中」，不乘 0.6）。另加青霧藥林（「低」）驗證 ×0.6。
    - 時間：春季取第 1 日，此時尚未進獸潮（`S.world` 首次獸潮在第 3–4 日），tideOn 為 false。
    - 狀態：每次實跑前用 JSON 快照還原 `S`。
11. **遇險率的量法**：
    - 先從 `camp()` 原文抽出 `night`／`risk` 兩行，在沙盒內以實作的 `isNight`、`perk` 求值，得到精確值。
    - 另外以 4000 個隨機 `S.rng` 真的跑 `camp()`，統計夜警開戰的比例，標準誤約 0.007。
    - 3fc260f 與 d0989ba 用相同的 `S.rng`，逐次比對開戰與否。
12. **對 d0989ba 的回歸**：用 `git show d0989ba:js/{data,game}.js` 把上一輪驗的版本載入另一個 vm，用同樣的狀態跑同樣的案例做比對。
13. **邊順序反轉**：在 `data.js` 跑完、`game.js` 執行前，在記憶體中改 `window.SHL_DATA`，不改檔案。
    - 反轉方式：反轉 `EDGES` 陣列，同時對調每條邊的 a／b。
    - 另外測：反轉 `NODES` 的鍵順序、兩者都反轉、EDGES 隨機打亂 50 種、EDGES＋NODES 隨機打亂 50 種。

    - 險值只用 base（官道 0.04、單段野徑 0.22、多段含野徑 0.30）。原因是：同時段、同 R 時，(時數, 野徑段數) 相同的兩條路線，其他乘項都一樣（夜間、超載、獸潮、R 都只看「是否含野徑」）。
15. **briefDanger 重建**：依 7.1b 公式，取灰窯到每個 `known()` 目的地的 `route()` 路線，計算 `min(0.85, base × R × (1+w_now) × wxRisk)`，取 R=1、晴、無獸潮，再用實作的 `riskTier` 分檔。

## 4. 規格待釐清

1. **飽食整數取整**：`passTime` 最後會做 `S.food = Math.round(S.food)`（`js/game.js:487`，原本就有）。結果如下：

   | 情況 | 規格值 | 實扣 | 原因 |
   |---|---|---|---|
   | 6h | 7.5 | 7 | 72.5 進位成 73 |
   | 13h | 16.25 | 16 | |
   | 冬 8h | 12.5 | 12 | |
   | 冬 12h | 18.75 | 19 | |

   - 規格 6.2 給的是非整數規格值，沒有寫儲存精度。
   - 0.5 一律進位，對玩家有利；連睡多晚會累積誤差。
   - 請數值設計師確認可以接受，或另訂取整規則。本輪的 1.25× 判定用未取整的扣減量。
2. **跨季睡眠的冬季倍率**：實作以 `passTime` 結束時刻（起床時）判冬（`js/game.js:476`）。
   - 秋→冬交界整段 ×1.25；冬→春交界整段不乘。
   - 規格 6.2 只寫「冬季再 ×1.25」，沒有寫跨季怎麼算。
3. **斷糧扣血是整段一次結算**：「飽食 5 睡 13 小時」在第 4 小時飽食就歸零，實作仍扣 3×13 = 39。
   - 規格 6.5 寫的是「取當前切片」（逐切片）。
   - 這是原本就有的行為；rest／bunk 有下限 1 擋住，但露宿、小憩、行走仍會多扣。
4. **露宿遇險率（E10）與實作不一致**（原本就有，沒有被本次修正改動）：
   - 實作仍是「起點或終點是黑夜就算 0.25」：12:00 睡 → 0.25（規格 0.12），17:00 → 0.25（規格 0.2256）。
   - 規格 7.1 把它列為新規則。這段程式看來不在 DEV-02 範圍內：`js/game.js:743` 的註解寫「SPEC-TIME 7.1 屬 DEV-TIME」。這是假設，需要確認由哪一包修。
5. **寒冷狀態**：規格 6.1／6.5 有寒意、寒顫，但實作裡沒有（`js/game.js` 中 cold／寒意／寒顫 0 處），所以「寒冷狀態下的 hp 下限」無法驗證。
6. **route() 第 4 層**：見 results §4.3。目前的實作在 NODES 順序改變時，赤石↔青霧、赤石↔古窯 4 對會換路。
   - 規格檔 7.1b 只要求送貨路線順序無關。這一點已經達成：EDGES 與 NODES 反轉、打亂，送貨六向都不變。
   - 本交辦的四層比較（18:13）要求全部路線順序無關，實作沒做到。
7. **「最險出城路線」的 tie**：在 briefDanger 重建裡，最大值由多條 base 0.30 的路線並列取得。
   - 若 UI 要顯示「哪一條最險」，需要規格訂 tie-break，例如沿用四層比較。
   - 檔位本身不受影響。
